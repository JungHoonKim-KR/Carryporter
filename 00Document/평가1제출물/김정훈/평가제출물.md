# 공부 1:AI 스토리북 저작 도구

## 핵심 AI 이론 및 기술 요약

`app.py` 파일은 최신 AI 기술들을 매우 실용적으로 조합하여 사용하고 있습니다. 이 코드에 나타난 핵심적인 AI 이론과 기술들은 다음과 같습니다.

### 1. 거대 언어 모델 (LLM) 활용 기술

이 앱은 **`Bllossom/llama-3.2-Korean-Bllossom-AICA-5B`** 라는 한국어 LLM을 '두뇌'처럼 사용합니다. 단순히 글만 쓰는 게 아니라 여러 지능적인 작업을 수행합니다.

### 가. 모델 경량화: 4비트 양자화 (Quantization)

`bnb_config = BitsAndBytesConfig(load_in_4bit=True, ...)
llm_model = AutoModelForCausalLM.from_pretrained(..., quantization_config=bnb_config, ...)`

- **이론**: 거대 언어 모델은 수십억 개의 파라미터(가중치)를 가져 메모리 사용량이 매우 큽니다. '양자화'는 모델의 가중치를 표현하는 데이터 타입의 정밀도를 낮추는 (예: 32비트 실수를 4비트 정수로) 기술입니다.
- **적용**: 이 앱은 `BitsAndBytes` 라이브러리를 통해 모델을 4비트로 로드합니다. 이 덕분에 VRAM이 적은 일반 소비자용 GPU에서도 거대 모델을 실행할 수 있으며, 추론 속도도 빨라집니다.

### 나. 프롬프트 엔지니어링 (Prompt Engineering)

LLM이 원하는 결과물을 내놓도록 '지시문(프롬프트)'을 정교하게 설계하는 기술입니다. 이 앱은 세 가지 다른 목적으로 프롬프트를 사용합니다.

1. **스토리 생성**: `generate_initial_story` 함수에서 주인공 설정, 문단 수, 문장 수, 표현 방식 등의 명확한 규칙을 제시하여 일관된 형식의 이야기를 생성하도록 유도합니다.
2. **핵심 장면 요약**: `analyze_text_for_english_scene` 함수에서 이야기 문단을 이미지로 만들기 가장 좋은 '핵심 시각적 장면'만 영어 명사구로 요약하도록 지시합니다.
3. **번역**: `translate_to_english` 함수에서 이미지 생성에 더 유리한 간결한 영어 표현으로 번역하도록 요청합니다.

### 2. 이미지 생성 모델 (Stable Diffusion) 활용 기술

이미지 생성에는 **`runwayml/stable-diffusion-v1-5`** 모델을 기반으로 사용합니다.

### 가. 잠재 확산 모델 (Latent Diffusion Model, LDM)

- **이론**: Stable Diffusion은 고해상도 픽셀 공간이 아닌, 압축된 '잠재 공간(Latent Space)'에서 이미지 생성 작업을 수행합니다. 노이즈를 점진적으로 제거해나가는 '확산(Diffusion)' 과정을 통해 이미지를 생성하며, 이 과정이 잠재 공간에서 일어나 매우 효율적입니다.

### 나. U-Net 아키텍처

- **이론**: U-Net은 확산 모델의 핵심 엔진으로, 각 단계에서 이미지에 포함된 노이즈를 예측하는 역할을 합니다. 텍스트 프롬프트 정보를 받아 해당 내용에 맞는 방향으로 노이즈를 제거하도록 학습되었습니다.

### 다. 파라미터 효율적 미세조정: LoRA (Low-Rank Adaptation)

`sd_pipe.unet = PeftModel.from_pretrained(sd_pipe.unet, lora_checkpoint_path)`

- **이론**: 수십억 개의 파라미터를 가진 거대 모델 전체를 특정 그림체로 다시 학습시키는 것은 엄청난 비용과 시간이 듭니다. LoRA는 기존 모델의 가중치는 그대로 두고, 아주 작은 규모의 가중치(어댑터)만 추가로 학습하여 덧붙이는 기술입니다.
- **적용**: 이 앱은 `sd_pipe.unet`에 미리 학습된 LoRA 가중치를 덧입힙니다. 이를 통해 적은 자원으로도 기본 Stable Diffusion 모델이 특정 스타일(코드에 따르면 "naruto character")의 그림을 잘 그리도록 '미세조정(Fine-tuning)'하는 효과를 얻습니다.

### 3. 멀티모달 (Multimodal) AI 시스템 구축

이 애플리케이션의 가장 큰 특징은 **두 가지 다른 종류의 AI 모델(LLM, Stable Diffusion)을 유기적으로 연결**하여 시너지를 낸다는 점입니다.

- **LLM (기획자/번역가 역할)**: 사용자의 추상적인 아이디어(이야기 주제)를 구체적인 텍스트(챕터별 이야기)로 만들고, 이 텍스트를 다시 이미지 생성 모델이 이해할 수 있는 시각적 프롬프트(영어 장면 요약)로 변환합니다.
- **Stable Diffusion (화가 역할)**: LLM이 전달해준 구체적인 시각적 프롬프트를 기반으로 실제 이미지를 그려냅니다.

이처럼 각기 다른 강점을 가진 모델들을 파이프라인으로 연결하여, 텍스트 입력만으로 글과 그림이 함께 있는 '스토리북'이라는 복합적인 결과물을 만들어내는 정교한 멀티모달 시스템을 구축한 것입니다.

### 4. 공학적 최적화

- **캐싱(Caching)**: `ImageCache` 테이블을 만들어 한 번 생성한 이미지의 프롬프트와 결과물 경로를 저장합니다. 동일한 프롬프트로 이미지 생성을 다시 요청하면 새로 생성하는 대신 저장된 이미지를 바로 반환하여 시간과 컴퓨팅 자원을 절약합니다.
- **재현성(Reproducibility)**: `torch.Generator().manual_seed()`를 사용하여 이미지 생성 시 시드(seed) 값을 고정합니다. 이를 통해 동일한 입력에 대해 항상 동일한 결과 이미지를 얻을 수 있습니다.

# 프로젝트 브랜치 전략

## 1. 브랜치 구조 요약

| **구분** | **브랜치명** | **설명** |
| --- | --- | --- |
| **최종 기록** | `master` | **전체 아카이브.** 코드 + 개발 문서 + 기획서 등 모든 산출물의 최종본 (배포용 아님) |
| **실서비스** | `release` | **사용자 서비스 최종판.** 실제 배포가 이루어지는 브랜치 |
| **통합 개발** | `develop` | **개발 최종판.** 모든 파트(AI, BE, FE)의 기능이 합쳐진 공간 |
| **개발 공장(?)** | `feature` | **파트별 조립 및 테스트 구역.** (예: `feature/Backend`) |
| **기능 개발** | `feature/[Part]/[Task]` | **세부 기능 구현.** (예: `feature/Backend/Auth`) |
| **핫픽스** | `hotfixes` | 개발은 완료했지만 **배포 과정에서 발생한 에러를 해결** |

---

## 2. 상세 브랜치 역할

### 🏛 master

- 프로젝트의 **가장 완벽한 형태의 기록**입니다.
- `develop`의 코드뿐만 아니라, **기획서, 설계도, API 명세서 등 모든 문서**를 포함합니다.
- 실서비스 배포용이 아닌, 프로젝트 전체를 아우르는 최종 저장소 역할을 합니다.

### 🌐 release(유저용 서버)

- **사용자가 만나는 실제 배포 브랜치**입니다.
- `develop`에서 검증이 끝난 코드가 이곳으로 합쳐지며, 합쳐지는 즉시 실서버에 반영됩니다.

### 🧪 develop(개발용 서버)

- 실제 배포(release) 전 테스트 브랜치
- 파트별 'feature'에서 검토가 완료된 기능들만 이쪽으로 들어올 수 있습니다.
- 파트별 'feature'에서 만들어진 새로운 기능이 병합되는 장소
- release 이전에 파트별로 서로 충돌이 없는지 확인

### 🎡 feature

- 기능 추가 브랜치 (ai, backend, frontend 등)
- 예시 feature/frontend/login-page

---

## 3. 작업 흐름

기능 하나가 개발되어 배포되기까지의 과정입니다. (예: 백엔드 로그인 기능)

1. **브랜치 생성:** `develop`을 바탕으로 본인이 개발할 `feature`브랜치 생성
    - git checkout -b feature/backend/login
2. **기능 구현:** 해당 브랜치에서 코드를 작성하고 커밋 및 푸시합니다.
3. **MR:** `feature/backend/login`→`develop`으로 MR을 보냅니다.
    - 다른 파트(AI, FE)와의 연동 테스트를 거칩니다.
    - 백엔드 팀원들의 코드 리뷰를 거쳐 **Approve**를 받으면 조립(Merge) 완료!
4. **리뷰:** MR요청을 리뷰어가 리뷰한다
    - 리뷰 후 문제 발견 시 comment : 이 코드는 왜 썼나요??
    - 리뷰 후 문제 미발견 시 comment : 굿
5. **최종 확인(Approve) & Merge** 
6. **배포 및 기록:**
    - `develop` → `release` (실제 배포 발생)
    - `develop` → `master` (문서 업데이트 및 최종 아카이빙)

---

## 4. 협업 규칙 (Ground Rules)

- **실수 방지:** 절대 `develop`이나 `release` 브랜치에 직접 Push하지 않습니다. 반드시 파트별 연습장(`feature/Part`)을 거쳐 MR로 합류합니다.
- **리뷰 우선:** 모든 MR은 파트원에게 검토를 받아야 합니다.
    - 리뷰어는 파트별로 맡아서 정합니다.
- **MR 양식: ..**
- **문서화:** 기능이 변경되거나 추가될 경우, `master` 브랜치에 반영할 문서(API, 명세 등)도 반드시 함께 업데이트합니다.
- 기타 추가 사항들…

---

## 5. 팁

- 브랜치에서 `feature/branch/login`은 feature 내부에 새로운 브랜치가 생기는 것이 아니라 feature 브랜치의 일부를 상세히 기술한 것일 뿐이다
    - 즉 feature 하위(?)의 모든 push는 feature에 적용되는 것이다
- MR과 PR는 같은 것이다
    - GItlab : Merge Request
    - Github : Pull Request

---

## 6. 정리

### 브랜치

- master
    - develop + 기타 문서
- release
    - 배포 환경
- develop
    - 개발 환경
    - MR : `develop`→ `release`
- feature
    - 개발 테스트
    - MR : `feature`→ `develop`
- hotfix
    - 긴급 버그 픽스
    - MR : `hotfix`→ `release`/ `hotfix`→ `release`

## **2. 핵심 내용**

# MQTT

## 정의

- Message Queue for Telemetry Transport
- 머신 대 머신 통신에 사용되는 표준 기반 메시징 프로토콜

![image.png](./image/image%209.png)

## 용어

| **MQTT 개념** | **단톡방 비유** | **실제 역할** |
| --- | --- | --- |
| **Broker (Mosquitto)** | **카카오톡 서버** | 모든 메시지를 전달해주는 중앙 서버 |
| **Topic (토픽)** | **채팅방 이름** | `orin/command/MAC주소`라는 이름의 방 |
| **Publisher (발행자)** | **메시지 전송자** | 명령을 내리는 **Spring Boot** |
| **Subscriber (구독자)** | **채팅방 멤버** | 명령을 기다리는 **라즈베리파이(오린카)** |
| **Payload (페이로드)** | **채팅 메시지** | "거실로 이동해"라는 **JSON 데이터** |

## 사용 이유

1. 빠른 통신을 위해
    - 헤더 크기가 2바이트 정도로 매우 작아, 하드웨어의 부하를 줄이고 빠른 통신이 가능
2. 비연결성 & 비동기 통신
    - 서로의 IP를 몰라도 브로커 주소만 알면 됨
3. 실시간 양방향 통신
    - 메시지를 던지면 즉각 반응 가능
4. 불안정한 네트워크 환경에 최적
    - Keep-Alive
        - 적은 패킷으로 연결 상태 계속 확인
    - QoS
        - 중요한 데이터는 네트워크가 불안정해도 전달 보장
    - LWT
        - 예기치 않게 종료해도 브로커가 즉시 서버에게 알려줌

**MqttConfig**

```java
@Configuration
public class MqttConfig {

    @Value("tcp://localhost:1883")
    private String brokerUrl;

    @Value("spring")
    private String clientId;

    @Bean
    public MqttConnectOptions mqttConnectOptions() {
        MqttConnectOptions options = new MqttConnectOptions();
        options.setServerURIs(new String[]{brokerUrl});
        options.setCleanSession(true);
        return options;
    }

    @Bean
    public MqttClient mqttClient() {
        try {
            MqttClient mqttClient = new MqttClient(brokerUrl, clientId, new MemoryPersistence());
            mqttClient.connect(mqttConnectOptions());
            return mqttClient;
        } catch (MqttException e) {
            throw new RuntimeException(e);
        }
    }
}
```

@RestController
public class **MqttController**{

    MqttPublisherService mqttPublisherService;

    public MqttPublisherController(MqttPublisherService mqttPublisherService) {
        this.mqttPublisherService = mqttPublisherService;
    }

    @PostMapping("/mqtt/publish")
    public void SendTopicAndMessage(@RequestBody MqttRequestDto mqttRequestDto) {
        mqttPublisherService.sendMessage(mqttRequestDto.getTopic(), mqttRequestDto.getMessage());
    }
}

**MqttService**

```java
@Service
public class MqttService {

    private MqttClient mqttClient;

    public MqttService(MqttClient mqttClient) {
        this.mqttClient = mqttClient;
    }

    public void sendMessage(String topic, String message) {
        try {
            Map<String, Object> payload = new HashMap<>();
            payload.put("device", "orin-ka-1");
            payload.put("command", message); // "test1"
            payload.put("timestamp", System.currentTimeMillis());
            String jsonString = new ObjectMapper().writeValueAsString(payload);
            mqttClient.publish(topic, new MqttMessage(jsonString.getBytes()));
        } catch (MqttException | JsonProcessingException e) {
            throw new RuntimeException(e);
        }
    }
}
```

- 잿슨 오린 보드 부팅 → AI관련 코드 파일 자동 Run → MQTT에 연결

## 사용자 요청

짐캐리의 동작은 라인트레이싱으로 가정하겠음

### **1단계: 사용자 접근**

- 사용자가 웹 브라우저를 통해 서비스 URL에 접속한다.

### **2단계: 프론트엔드 제공**

- **Nginx** 서버가 EC2 내부에 빌드된 **React** 정적 파일을 사용자에게 전달한다.
- 사용자는 화면에서 로봇 제어 인터페이스(버튼 등)를 확인한다.

### **3단계: 명령 발생**

- 사용자가 화면에서 "짐캐리(라인트레이싱) 시작" 버튼을 클릭한다.

### **4단계: API 호출**

- React 앱이 백엔드 서버의 API 엔드포인트(`POST /api/robot/start`)로 HTTP 요청을 보낸다.

### **5단계: 백엔드 처리 및 IoT 명령 하달**

- **Spring Boot** 서버가 요청을 수신하여 비즈니스 로직을 처리한다.
- **MQTT** 프로토콜을 사용하여 라즈베리파이가 구독 중인 토픽으로 "라인트레이싱 시작" 메시지를 발행(Publish)한다.

### **6단계: 로봇 동작 개시**

- **라즈베리파이**가 MQTT 메시지를 수신하고 주행 데몬을 실행한다.
- 분석 모듈인 **젯슨**을 호출하며 카메라를 통해 바닥의 라인을 실시간으로 촬영한다.

### **7단계: 영상 분석 및 데이터 피드백**

- 젯슨이 카메라 영상을 실시간으로 분석하여 라인의 위치를 파악한다.
- 조향에 필요한 방향(좌/우/직진)과 **라인까지의 거리**를 계산한다.
- 분석된 수치를 라즈베리파이의 제어 프로그램으로 즉시 전달한다.

### **8단계: 실시간 제어 루프 반복**

- 라즈베리파이는 수신된 방향/거리 데이터를 기반으로 모터 속도와 각도를 정밀하게 제어한다.
- 목표 지점에 도달하거나 정지 명령이 들어올 때까지 **6단계와 7단계를 초당 수십 회 반복**하며 주행을 지속한다.

## 주요 컴포넌트 역할 요약

- **React**: 사용자 인터페이스 제공
- **Nginx**: 웹 서버 (정적 파일 제공)
- **Spring Boot**: API 서버 (비즈니스 로직 + IoT 통신)
- **MQTT**: Spring Boot ↔ 라즈베리파이 간 메시지 전달
- **라즈베리파이**: 물리적 동작 제어 (짐캐리 실행)
- **잿슨**: 영상 분석 엔진 (방향/거리 계산)
